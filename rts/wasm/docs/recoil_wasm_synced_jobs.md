# Wasm jobs and local sync verification

Implemented and verified locally on amd64 Linux on 2026-10-12. See the
[dated report](recoil_wasm_synced_jobs_report_2026-10-12.md) for results,
measurements, provenance, and remaining verification limits. The
[all-environment/profiling follow-up](recoil_wasm_jobs_followup_2026-10-12.md)
records the newer code checkpoint and acceptance checks.

## Getting started

1. Choose the submitting module's world and package it in the usual Wasm
   manifest. Both job imports are available in all seven worlds; the engine
   needs no extra job switch or separate thread pool.
2. Export the input scratch helpers and a pure work function using the ABI
   below. Serialize all needed state into input bytes. Prefer a small dedicated
   worker module when the game module has a large initial memory.
3. In the submitting module, register `spring::export_job_results!` once. Handle
   success and worker errors there; copy result bytes if they must outlive the
   callback. Submission can also fail immediately and returns an SDK error.
4. Call `spring::jobs::submit` or `submit_to` from an allowed callback. Save the
   returned ID with the request's meaning. Synced IDs span multiple owners, so
   do not assume this module's next ID is always its previous ID plus one.
5. Apply the result at the documented delivery boundary. The engine waits and
   delivers in submission order; changing worker counts cannot move a synced
   result to another sim frame. There is no readiness polling or shared memory.

For a complete buildable example, use the
[Rust guest](../../../test/wasm_api/guests/synced_jobs_guest/src/lib.rs):

```sh
cargo build --release --locked --target wasm32-unknown-unknown \
  --manifest-path test/wasm_api/guests/synced_jobs_guest/Cargo.toml
```

Package its `recoil_wasm_synced_jobs_guest.wasm` output in an isolated test game
and declare a module in `LuaRules/wasm/manifest.txt`, for example:

```text
module(sync-jobs-test, LuaRules/wasm/jobs.wasm, rules-synced, 999, 1.0.0)
```

The replay runner's `--fixture` option performs this overlay automatically.
The fixture asserts its result order and private state; run it in a fresh
isolated scenario, rather than adding it to a production game. Local-world
examples are generated by
[prepare_jobs_environments.py](../../../test/wasm_api/prepare_jobs_environments.py).
Use [Tracy timelines and CPU sampling](recoil_wasm_jobs_profiling.md) to choose
job sizes: small jobs can cost more to instantiate and dispatch than to run
inline, and the barrier exposes the slowest work in the batch.

## Execution contract

Every Core environment can submit an export name and input bytes: RulesSynced,
GaiaSynced, RulesUnsynced, GaiaUnsynced, UI, Menu, and Intro. An accepted
submission returns a nonzero increasing `u32` job ID. Synced IDs are global across
the two synced worlds; local IDs are scoped to the submitting module.
Inputs are copied before the import returns; subsequent changes to guest memory
cannot change the job. Rejected submissions consume no ID.

Synced submissions are accepted during simulation-frame callbacks, including
result callbacks; synced initialization and between-frame callbacks cannot submit.
Local submissions are accepted during initialization and between local updates,
including input/draw callbacks. There is no polling or readiness API.

For synced owners, at the end of frame F, after `GameFramePost`, the engine seals the batch and
dispatches it through its existing background thread pool. At the start of F+1,
after advancing the frame number and before ordinary simulation updates or
`GameFrame`, it waits for the entire batch and invokes result callbacks on the
simulation thread in **global submission order**, including submissions from
different modules. A slow early job never permits later jobs to arrive early.
Result callbacks may submit jobs for delivery at F+2.

Each local module owns a separate queue. At the end of its Update, its current
window is sealed; results arrive in submission order before its next Update,
independently of simulation pause or game-frame number. Input/draw submissions
between those boundaries enter the next window, so they seal after the following
Update and arrive before the Update after that. Intro uses DrawLoadScreen as a
local boundary during loading. Each system pumps only its own modules, even if
several standalone systems coexist.

A synced owner can target either synced world. A local owner can target another
module in its own environment and NativeInterface system. Cross-category or
cross-system targets are rejected. Local queue IDs, quotas, readiness, callbacks,
and timing never enter the synced queue or checksum. Local callback fuel resets
at the local boundary and is shared with that update; UI read perspective and
Rml context ownership are preserved during result callbacks.

Each job creates a fresh Wasmtime store, linker, and instance. Only immutable
compiled code is reused. Linear memory, mutable globals, and tables are private
and start from the module's initial contents, **not the live rules instance's
state**. Per-job instances do not run the rules initialization callback. A Wasm `start`
function still runs during instantiation under the job fuel budget and cannot
call host imports. Include all required state in the input bytes. Workers cannot call any
host import: imported functions are linked as traps, including engine queries,
clocks, RNG, and job submission. The submitting instance's result callback can
use its usual synced imports.

The worker owns a reference to the source runtime's engine and compiled module.
It inherits the same deterministic engine settings, memory/table limits, result
limit, and instruction-fuel configuration. NaNs are canonicalized, relaxed SIMD
uses deterministic settings, and Wasm threads/shared memory remain disabled.
Each job receives a fresh configured fuel allowance covering its helpers and
computation. Fuel zero retains the runtime's existing unlimited policy. Synced
result callbacks and that frame's other callbacks share one ordinary frame
budget; receiving results does not grant additional frame fuel.

Unloading a submitting module drains workers and cancels its pending deliveries.
Accepted jobs owned by other modules retain their compiled worker program even
if its source module unloads. A new game's frame zero resets the global ID
sequence. No job is delivered before its barrier. Host allocation/runtime
failures at execution terminate simulation before publishing any result from
that synced batch; they do not become schedule-dependent success/error game decisions.
A local execution/dispatch failure faults its submitting module instead.

This follows QTPFS's private task outputs, background barrier, and ordered merge.
The barrier can delay real time, but cannot move a result to another sim frame.
The pool count includes the simulation thread; one thread executes serially.

## Core ABI

Imports are available in all seven Core environments, under `spring:jobs`:

| Import | Wasm signature | Meaning |
|---|---|---|
| `submit` | `(name_ptr:i32, name_len:i32, input_ptr:i32, input_len:i32) -> i64` | Export in the submitting module |
| `submit-to` | `(module_ptr:i32, module_len:i32, name_ptr:i32, name_len:i32, input_ptr:i32, input_len:i32) -> i64` | Export in a named, already loaded compatible module; result belongs to the submitter |

Pointers and lengths are unsigned 32-bit values. Names are length-delimited,
without a terminating NUL. The return value packs the ID in the low 32 bits and
the ordinary Core status in the high 32 bits. Zero status means success.
`submit-to` with an empty module name has the same raw-ABI meaning as `submit`;
the Rust `submit_to` wrapper requires a nonempty explicit name.

Admission statuses include `InvalidArgument=1` (empty/oversized export name or
oversized input), `OutOfBounds=2`, `NotFound=3` (target missing, incompatible, or
faulted), `NotAvailable=4` (no result exports), `InvalidState=5` (outside the
submission window), and `BufferOverflow=9` (batch/ID limits).
Job imports validate in every environment. Missing worker exports
are reported asynchronously, rather than during admission. Host-work budget
exhaustion traps the submitting instance as with other imports.

A worker must export:

| Export | Wasm signature |
|---|---|
| `memory` | Non-shared linear memory |
| `SPRING_JOB_INPUT_BUFFER` | `() -> i32`, writable scratch pointer |
| `SPRING_JOB_INPUT_CAPACITY` | `() -> i32`, scratch byte capacity |
| Chosen work export | `(input_ptr:i32, input_len:i32) -> i64` |

The work return packs the output pointer in the low 32 bits and byte length in
the high 32 bits. The engine validates the range and copies it into engine-owned
bytes before destroying the instance. Returning part of the input buffer is
allowed. Scratch helpers must themselves avoid host imports.

The submitting module must export all three result exports together:

| Export | Wasm signature |
|---|---|
| `SPRING_JOB_RESULT_BUFFER` | `() -> i32`, scratch pointer in the live submitting instance |
| `SPRING_JOB_RESULT_CAPACITY` | `() -> i32`, scratch byte capacity |
| `spring:jobs/result` | `(id:i32, job_status:i32, output_ptr:i32, output_len:i32) -> ()` |

Worker status has a separate namespace:

| Status | Value | Meaning |
|---|---:|---|
| Ok | 0 | Output bytes available |
| InvalidExport | 1 | Missing/wrong-signature helper, memory, or work export |
| Trapped | 2 | Guest trap, forbidden import, or exhausted job fuel |
| InputTooLarge | 3 | Input does not fit worker scratch/range |
| InvalidOutput | 4 | Output range or byte limit invalid |
| RuntimeFailure | 5 | Host/runtime failure; synced simulation terminates or the local owner faults before delivery |

Guest execution errors deliver an empty output with the corresponding status.
Human-readable trap diagnostics are not exposed as synced bytes. A result scratch
buffer that is too small or out of bounds, or a callback that traps/exhausts its
budget, faults the submitting module.

Fixed limits: 256 accepted jobs and 16 MiB aggregate input per window; globally
per sim frame for synced owners, per module/update window for local owners.
Inputs are at most 1 MiB per job and export/module names at most 256 bytes. Output is bounded
by both 1 MiB and the runtime's `resultBytesLimit`. IDs never wrap into valid
reused IDs; admission fails after exhausting the `u32` sequence. Limits are
independent of local thread count.

## Rust SDK

`spring::jobs::{submit, submit_to}` return the SDK's `Result<JobId>`. Register
the live result buffer and callback once. The macro requires a handler accepting
any borrowed lifetime; a handler requiring permanent (`&'static`) result bytes
does not compile:

```rust
fn on_result(id: spring::jobs::JobId,
             result: core::result::Result<&[u8], spring::jobs::JobError>) {
    // Apply by id, or store owned bytes for later. The slice lives only here.
}
spring::export_job_results!(on_result, 4096);

// From a synced frame callback, after "navigation-worker" is loaded:
let id = spring::jobs::submit_to("navigation-worker", "find-route", &snapshot)?;
```

Export the worker scratch helpers and work function separately. A small dedicated
worker module avoids instantiating all of a large rules module's initial memory.
The engine's [game fixture](../../../test/wasm_api/data/synced_jobs/jobs_in_game.wat)
demonstrates the complete ABI, copied inputs, next-frame callbacks, private globals,
integer/float equality against inline work, and both submission imports. The
[worker fixture](../../../test/wasm_api/data/synced_jobs/worker.wat) also exercises
fuel, traps, NaNs, memory limits, and output copying.

The [Rust SDK fixture](../../../test/wasm_api/guests/synced_jobs_guest/src/lib.rs)
uses these wrappers and macros in an actual headless game. Its `external-worker`
feature targets a distinct 64 KiB module supplied with runner `--worker-fixture`
from [dedicated_worker.wat](../../../test/wasm_api/data/synced_jobs/dedicated_worker.wat).

The [result-chain fixture](../../../test/wasm_api/data/synced_jobs/result_chain.wat)
exports only `GameFramePost` and the result callback. It reads the current engine
frame inside result callbacks and resubmits both jobs there, checking that callbacks
have the new frame's budget and admission context independently of `GameFrame`.

## State checksums and diagnosis

After `GameFramePost` and batch sealing, the engine hashes every synced module's
complete linear memory with XXH3-64, sorted by module name. It mixes memory size,
module SHA-512 identity, environment, fault state, memory hash, and job submission
hash into the existing `CSyncChecker` checksum. The job hash includes IDs, frames,
worker identity/runtime configuration, export names, and copied input; it never
reads background completion or worker outputs. Unsynced modules are excluded.

Game-owned `gamedata/modrules.lua` setting `system.WasmStateHashInterval` controls network
checksum cadence (default 1, minimum 1). Client-local settings cannot change it.
Hashing a large memory every frame costs memory bandwidth. Dirty-page tracking
and per-game subsystem digests are future optimizations.

Local configuration settings:

| Setting | Default | Meaning |
|---|---|---|
| `WasmSyncLog` | empty | JSONL filename; if set, inspect every frame regardless of network cadence |
| `WasmSyncDumpFrame` | -1 | With logging enabled, dump all synced memories at this frame beside the log |
| `WasmSyncStopFrame` | -1 | With logging enabled, diagnostic exit after the selected frame |

Each row contains `frame`, actual pool `workers`, `engine` (checksum before this
frame's Wasm mix), `checksum` (after it), `synccheck`, and per-module `name`,
`identity`, `environment`, `bytes`, `hash`, `jobs_hash`, `faulted`. The engine
checksum is cumulative and therefore includes earlier frames' Wasm contributions.
Memory dumps use `.frame-F.module-I.bin`, where I is the sorted module index.
Linear-memory hashing does not inspect live globals/tables; those are outside
this verification scope. Private worker globals are separately tested for reset.

The local runner rejects gaps/truncation, faults, absent required modules, builds
without SYNCCHECK, unexpected worker counts, and recorded desync warnings. It
reports the first differing frame and module (or engine checksum). Equal worker
counts with equally missing/faulted game code cannot falsely pass.

```sh
python3 test/synctest/wasm_sync_replay.py run --spring /absolute/runtime/spring-headless \
  --game /absolute/pinned/game.sdd --demo /absolute/scenario.sdfz \
  --output /absolute/new-output --threads 1 4 --frames 1200 \
  --record-first --instruction-fuel 1000000000 --fixture /absolute/jobs.wasm
python3 test/synctest/wasm_sync_replay.py compare /absolute/a.jsonl /absolute/b.jsonl
python3 test/synctest/wasm_sync_replay.py memory-diff /absolute/a.bin /absolute/b.bin
```

`--record-first` extracts the pinned scenario from a version-5 demo, records it
on the new engine, then replays that **same new demo** for every worker count.
It compares complete frame logs both across worker counts and against the recording.
It preserves configs, scripts, logs, demos, results, and SHA-256 provenance in
fresh isolated directories. Source game files are read-only inputs; only the
isolated manifest and minimal test module are overlaid. Existing output is never
overwritten. `--timeout` is a per-engine-process bound; `--frames` is inclusive.
Old demos predating this checksum change require the explicit diagnostic option
`--allow-recorded-desync`; final acceptance should use fresh recordings without
that exception. No CI or remote publishing is required by this runner.
