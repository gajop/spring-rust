# Recoil Wasm API & Code Generation

## Purpose

Generate native Rust and Wasm bindings from one semantic description of the Spring NativeInterface API.

The surface is too large to maintain manually. Correctness should scale with the number of distinct API/type patterns, not the number of functions.

## Current starting point

`rust/crates/spring-native-codegen` already parses NativeInterface headers with libclang and has a structural model roughly equivalent to:

- API functions;
- query/result structs;
- primitives;
- records;
- pointers;
- arrays;
- function pointers.

Today, higher-level Rust semantics such as strings, pointer/count slices, option-presence fields, and callbacks are inferred later by renderer heuristics.

That is sufficient for the current native generator, but not sufficient as the source for multiple transports.

## Target semantic model

Introduce a transport-neutral API model containing at least:

- API module/interface;
- function name;
- query and result semantics;
- input/output fields;
- scalar types;
- enums;
- records;
- fixed arrays;
- strings and bytes;
- lists/slices;
- pointer/count relationships;
- optional values;
- errors/results;
- IDs/handles/resources;
- callbacks and callback lifetime;
- read-only versus mutating operation;
- execution-environment applicability;
- visibility-sensitive result marker where relevant to LuaUI;
- interface/version identity;
- manual/unsupported lowering marker.

Unknown or ambiguous shapes are generator errors unless explicitly excluded.

## C metadata

C-layout relationships should be declared next to the C declaration when the relationship cannot be recovered safely from the type itself.

Examples of metadata worth making explicit:

- pointer field paired with count field;
- optional field paired with presence boolean;
- string ownership/lifetime;
- callback + user-data + destroy-callback relationship;
- handle/resource meaning.

Prefer Clang-visible annotations/macros that disappear in normal C/C++ compilation.

Do not encode these relationships only in field order.

## WIT interface structure

WIT does not need to mirror the 44 NativeInterface C headers one-for-one.

Generate stable WIT interfaces based on:

1. coherent Spring API grouping;
2. execution-environment availability;
3. WIT linking/versioning constraints.

If functions from one C API module are present in different environment sets, split them into separate WIT interfaces rather than adding runtime stubs for unavailable functions.

Keep the grouping coarse. Interface splitting should happen because execution-environment API surfaces actually differ or versioning requires it.

## Execution-environment matrix

The semantic model carries environment applicability.

Initial environments:

- `rules-synced`;
- `rules-unsynced`;
- `gaia-synced`;
- `gaia-unsynced`;
- `ui` later.

Worlds are generated by composing the interfaces applicable to an environment.

Synced/unsynced is therefore primarily static in the generated world, not a dynamic permission attached to every call.

## Generated outputs

The shared model should drive:

### Native Rust

Preserve the existing `spring-native` functionality, but move it onto the shared semantic model.

### Wasm WIT

Generate WIT interfaces/worlds for each execution environment.

### C++ Wasm host adapters

Generate callout adapters that:

1. accept Component Model values;
2. validate them;
3. build NativeInterface query structs;
4. call the existing API table;
5. translate result/error values back.

### Wasm Rust SDK

Generate or wrap `wit-bindgen` output so the module-facing API resembles the native Rust API rather than exposing raw WIT transport details.

### Normalized signature artifacts

Emit a machine-readable representation, e.g. JSON, used by parity/signature tests.

## Public Rust values

The default public API should use safe owned semantic values.

Reasons:

- NativeInterface currently has scratch-backed/pointer-bearing result shapes.
- Those pointers cannot cross Wasm.
- Trying to expose a shared borrowed API safely requires enforceable invalidation lifetimes.
- Owned values provide one simple source-level API immediately.

Rules:

- no pointer-bearing `spring_native_sys` record appears in a safe public result;
- nested pointer-bearing structures become generated semantic structs;
- strings become Rust strings;
- flat pointer/count arrays become vectors/slices as appropriate;
- explicit owned conversions are the normal path.

Optional scoped/zero-copy APIs can be added later for measured hot paths without changing the default API.

## Errors

Native `Error { code, message }` is a transport detail.

The semantic model should expose stable error codes/categories.

Detailed host messages are not automatically part of the Wasm API; they may contain host paths or other implementation data and cost guest allocation on every error.

## Callins

Callins need one canonical machine-readable inventory because name-to-query/result mapping is not always derivable by convention.

A practical source can be a simple declaration file such as `Callins.def`.

Each callin entry should capture:

- callin name;
- semantic query/result type;
- applicable execution environments;
- optional export/default behavior;
- aliases/shared event shape;
- boolean/result aggregation rule;
- callback/re-entry classification if relevant.

Generate from this inventory:

- native function-pointer declarations/loading;
- Rust module trait methods;
- native Rust export trampolines;
- WIT exports;
- Wasm callin dispatch glue;
- normalized signature data.

Engine-side conversion remains in `NativeInterfaceEventClient`.

## Versioning

Native ABI versioning remains unchanged.

Wasm interfaces are versioned independently.

The implementation must define:

- when an interface gets a new incompatible version;
- how long old interfaces are retained;
- how additive changes are handled by the pinned Wasmtime/WIT tooling;
- module minimum engine/API version diagnostics.

Version behavior must be verified in the runtime spike rather than inferred from semver names alone.

## Generator validation

Generation should produce a summary:

- total functions;
- automatically lowered;
- explicitly annotated;
- manual/special;
- unsupported;
- per-environment interface counts.

The build fails on:

- unknown semantic types;
- missing query/result records;
- ambiguous pointer relationships;
- functions silently skipped by a renderer;
- unassigned callins;
- an environment world referencing an unavailable interface.

Generated code is reproducible and never manually edited.
